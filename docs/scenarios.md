# RideOps MVP 业务场景边界

本阶段围绕共享出行客服固定三个业务场景；事故中流程是唯一使用 LangGraph + HITL 的写入编排闭环。

## 场景一：出行前

用户在开始用车前，希望完成：

1. 查询附近可用车辆
2. 路线和费用预估
3. 预约车辆
4. 取消尚未使用的本人预约

当前 MVP 已完成合成数据版本：

- 本地 SQLite 查询车辆及持久化预约状态
- 高德 MCP 路线查询（未配置 Key 时自动回退至合成路线）
- RideOps 自主计价，并明确标注地图来源与计价来源
- 预约创建与取消均使用幂等键
- 取消预约校验归属，且只在车辆仍处于预约占用状态时恢复为可用

## 场景二：长租咨询

用户可查询城市、租期与预算条件下的长租库存和价格；确认后系统只创建后续跟进线索，不虚构支付、签约或真实租赁订单。

- SQLite 保存合成长租库存、价格、押金和最短租期
- 返回月租/日租混合计算、预算判断与假设
- 创建线索要求确认引用与幂等键

## 场景三：事故中

用户报告车辆事故、受伤、车辆损坏或订单仍在计费时，系统完成：

```text
收集信息
→ 查询订单和车辆
→ 检索事故政策
→ 信息不足时追问
→ 生成待执行动作
→ 人工审批
→ 写入订单/车辆/事故工单
→ 只读回读最终状态
```

当前 MVP 已完成该闭环的合成数据版本：

- SQLite 持久化订单、车辆、工单和 Run 状态
- HTTP 主流程通过普通业务 Service / Repository 执行；相同业务能力也已通过 FastMCP stdio 暴露
- 简单 LangGraph 准备图和执行图
- 审批前不产生写入
- 批准后执行三个幂等写动作
- 拒绝后安全结束
- 重复 Resume 不重复产生副作用
- 前端通过普通 HTTP 请求展示真实 Run 状态

当前仍未实现：真实模型调用、复杂 Checkpoint、SSE、真实企业系统和 Redis。
